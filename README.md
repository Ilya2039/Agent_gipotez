## Agent Gipotez — Telegram + FastAPI (GigaChat)

### Что делает агент
ИИ‑агент формирует гипотезы развития бизнеса на основе клиентских материалов и диалога. Два режима работы:
- Telegram‑бот (aiogram 3)
- FastAPI с одной ручкой `/chat` (движок — LangGraph)

Диалог: префейс (Шаг 1/3) → сложности → discovery (до 5 вопросов) → 3 гипотезы (каждая с 2–3 вопросами). Сохранение согласованных гипотез в `gipotez/all_gipotez.txt`.

### Как запускать
- Telegram:
```bash
python main.py --mode tg
```
- FastAPI:
```bash
python main.py --mode api --host 0.0.0.0 --port 8000
```

Переменные окружения (`.env`):
```env
TELEGRAM_BOT_TOKEN=xxxx
GIGACHAT_AUTH=xxxx
GIGACHAT_MODEL=GigaChat-2-Max
GIGACHAT_TEMPERATURE=0.8
GIGACHAT_TIMEOUT=60
GIGACHAT_PROFANITY_CHECK=false
```

### Файлы и назначение
- `main.py` — вход, выбор режима `--mode tg|api`.
- `requirements.txt` — зависимости (aiogram, fastapi, uvicorn, langgraph, langchain‑community/core и т.д.).
- `app/llm/client.py` — клиент GigaChat на LangChain; метод `invoke(prompt, system)`.
- `app/prompts/core.py` — промпты: discovery‑вопросы, гипотезы, альтернативы, вопросы к встрече, фильтрация целей, извлечение договорённостей, уточнение гипотез.
- `app/parsers/docx_parser.py` — DOCX → JSON (заголовки/абзацы/таблицы) и извлечение плоского текста.

- Telegram (`app/bot/`):
  - `bot_app.py` — состояние/хендлеры/оркестрация, сохранение гипотез в `gipotez/all_gipotez.txt`.
  - `handlers.py` — регистрация хендлеров.
  - `preface.py` — Шаг 1/3 (3 сообщения), вопрос о сложностях, переход к discovery.
  - `flows.py` — генерация вопросов, финализация 3 гипотез, корректировка.
  - `files.py` — загрузка `.docx/.json`, парсинг, мердж, дебаунс.
  - `texts.py` — тексты и подписи кнопок.
  - `ui.py` — клавиатуры (корректировать/ещё — верхний ряд; согласиться — отдельной строкой).
  - `states.py` — FSM.
  - `utils.py` — лог/контекст/JSON‑утилиты.

- FastAPI (`app/api/`):
  - `graph.py` — весь движок диалога и сборка LangGraph (узлы, состояния, сохранение гипотез).
  - `server.py` — только FastAPI, одна ручка `POST /chat`, прокси к `graph.invoke(...)`.

Артефакты:
- `gipotez/all_gipotez.txt` — накопительный файл согласованных гипотез (plain text).
- `logs/` — служебные файлы (TG).

### FastAPI — протокол `/chat`
Запрос (JSON):
- `session_id`: строка — идентификатор сессии
- `user_input`: строка | null — ответ пользователя
- `docs`: строк[] | null — сырые тексты
- `docs_paths`: строк[] | null — пути к файлам (сервер сам прочитает и извлечёт текст)
- `action`: "correct" | "more" | "agree" | null

Ответ:
- `messages`: строк[] — сообщения агента
- `stage`: строка — стадия диалога (`init | await_goals | await_difficulties | discovery | final`)
- `idx`: число — номер текущего вопроса discovery

→ Пересоберёт 3 гипотезы с учётом правок (как в Telegram). Можно снова `agree`.


   Я автоматически начну вопросы через пару секунд после последнего файла. Если файлов нет — напишите /skip»

2) После первой загрузки файла бот выводит префейс (ровно текстом):
   «Я умею выявлять гипотезы… (4 абзаца)»

3) Шаг 1/3 — «Из протоколов встреч видно текущие договорённости:»
   - LLM извлекает пункты из контекста (строгий JSON массив строк).
   - Бот показывает нумерованный список и спрашивает об актуальности.

4) Шаг 2/3 (опционально) — «договорённости, которые уже должны быть выполнены:»
   - LLM ищет дедлайны < сегодня. Если есть — показывает список и спрашивает про исполнение/сложности.
   - Если нет — шаг пропускается.

5) Вопрос о целях (THEME_PROMPT):
   - Ответ фильтруется промптом `build_filter_goals_prompt` (игнорируем «пропустить/хз/не знаю/да/нет/…»), на выходе JSON массив валидных целей.
   - Формируется список для ранжирования: сначала валидные цели пользователя, затем договорённости из Шага 1/3.
   - Бот выводит нумерованный список и инструкцию: «Расставьте в порядке убывания приоритетов… Пример: <случайная перестановка 1..N>».

6) Динамические вопросы (до 5):
   - На каждом шаге LLM решает «спросить/попросить файл/выдвинуть гипотезу/стоп».
   - «Не знаю» распознаётся промптом и не повторяется; «unknowns» копятся для финального блока.
   - Сгенерированный вопрос дополняется «Примером ответа». 

7) Финал — 3 гипотезы в строгом формате:
   - Каждая гипотеза выводится так:
     - `<b>Гипотеза: Текст гипотезы</b>`
     - пустая строка
     - `Причина: <25–40 слов>`
     - пустая строка
     - `- Вопрос 1`\n`- Вопрос 2`\n`- Вопрос 3`
   - В конце: «Будет полезно узнать у клиента:» со списком вопросов, где ответ был «не знаю».
   - Кнопка «Сгенерировать ещё» — новый раунд (вопросы и гипотезы не повторяются, задаём avoid‑списки).

### Что важно
- Темы (manual) мы не спрашиваем — шаг отключён. Контекст собирается из загруженных материалов и ответов.
- Все тексты UI фиксированы и выведены в код/`app/bot/texts.py` согласно требованиям.
- Повторов вопросов и гипотез нет: поддерживаются списки `avoid_questions_all` и `avoid_hypotheses`.

### Логи
- Приложение: `logs/bot.log`
- Диалоги: `logs/dialogs/<chat>_*.txt`

### Разработка
- Промпты: `app/prompts/core.py`
  - `build_extract_agreements_prompt` — текущие договорённости.
  - `build_extract_overdue_agreements_prompt` — просроченные по дедлайну.
  - `build_filter_goals_prompt` — фильтрация целей из свободного текста.
  - `build_generate_*` — вопросы/гипотезы/альтернатива/валидирующие вопросы.
- Потоки: `app/bot/flows.py` — генерация следующего вопроса, финализация гипотез (в т.ч. формат).
- Оркестратор: `app/bot/bot_app.py` — шаги префейса, хранение состояния, LLM‑вызовы.

### Ограничения и расширения
- Все промпты — строго JSON (кроме простых текстовых ответов). Если LLM вернул невалидный JSON — предусмотрены фолбэки.
- Для сложных правил ранжирования/фильтрации можно заменить промпт на детерминированную проверку.
